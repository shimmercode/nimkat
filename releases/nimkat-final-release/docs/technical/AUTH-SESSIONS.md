# احراز هویت و نشست‌ها — مرحلهٔ امنیت

## وضعیت و مرزها

این تغییر ورود و نشست‌ها را اصلاح می‌کند؛ تأیید امنیت کل سامانه یا آمادگی مالیِ
production نیست. دیتابیس فعلی SQLite است و Redis/PostgreSQL هنوز جایگزین نشده‌اند.
ارسال پیامک واقعی هنوز متصل نیست؛ در production بدون adapter، درخواست OTP با 503
رد می‌شود. حالت توسعه همچنان `devCode` را فقط در پاسخ درخواست OTP نشان می‌دهد.
کد در لاگ سرور چاپ نمی‌شود.

## مدل نشست

توکن‌ها opaque و تصادفی ۲۵۶بیتی‌اند، نه JWT خودساخته. این تصمیم امکان ابطال فوری
نشست در سرور را می‌دهد و نباید با تکمیل JWT/Redis سند فنی اشتباه گرفته شود.
دیتابیس فقط SHA-256 توکن‌های پرآنتروپی و شناسهٔ نشست را نگهداری می‌کند.

| کوکی | مسیر | HttpOnly | طول عمر |
|---|---|---|---|
| nk_access | /api | بله | ۱۵ دقیقه |
| nk_refresh | /api/auth | بله | حداکثر ۷ روز از ایجاد نشست |
| nk_csrf | / | خیر | هم‌طول نشست |

همه host-only و SameSite=Lax هستند و در production حتماً Secure می‌شوند.
`nk_csrf` کلید ورود نیست؛ برای درخواست‌های تغییردهنده در `X-CSRF-Token` ارسال
و با هش ذخیره‌شدهٔ همان نشست تطبیق داده می‌شود. Origin و Sec-Fetch-Site نیز بررسی
می‌شوند. احراز هویت با Bearer قدیمی دیگر پذیرفته نمی‌شود.

## API

- `POST /api/auth/otp/request` — شمارهٔ معتبر، تولید crypto.randomInt، اعتبار ۲ دقیقه.
- `POST /api/auth/otp/verify` — حداکثر ۵ تلاش؛ مصرف یک‌باره در تراکنش؛ ایجاد نشست و کوکی؛ بدون token در JSON.
- `GET /api/auth/me` — کاربر نشست جاری؛ برای مهمان `{user:null}`؛ نشست نیازمند تمدید: 401.
- `POST /api/auth/refresh` — نیازمند refresh cookie و CSRF؛ چرخش access/refresh.
- `POST /api/auth/logout` — ابطال همان نشست و پاک‌کردن کوکی‌ها؛ idempotent.
- `POST /api/auth/logout-all` — ابطال تمام نشست‌های همان کاربر؛ نیازمند auth و CSRF.

استفادهٔ دوباره از refresh مصرف‌شده، در صورت داشتن اثبات CSRF همان نشست، آن نشست
را باطل می‌کند. عمر نهایی ۷روزه با چرخش تمدید نمی‌شود. سرقت صرفِ refresh بدون CSRF
باعث ابطال نشست شخص دیگر نمی‌شود.

## کلاینت

- هیچ access/refresh در localStorage یا sessionStorage نوشته نمی‌شود.
- credential قدیمی `nimkat_token` هنگام راه‌اندازی حذف می‌شود؛ کاربران قبلی باید دوباره وارد شوند.
- bootstrap با `/auth/me` و تمدید خودکار از کوکی انجام می‌شود.
- یک refresh هم‌زمان در هر tab؛ Web Locks در مرورگرهای پشتیبان، درخواست‌های tabهای مختلف را هماهنگ می‌کند.
- retry درخواست اصلی پس از تمدید، حداکثر یک بار؛ خطای CSRF یا OTP باعث حلقهٔ refresh نمی‌شود.
- خروج فقط پس از موفقیت ابطال سمت سرور، وضعیت UI را پاک می‌کند؛ قطع شبکه خروج جعلی نشان نمی‌دهد.

## OTP و محدودسازی

کد با HMAC-SHA256 و secret سرور، همراه شماره، هش می‌شود؛ plaintext در DB وجود ندارد.
تلاش‌های باقی‌مانده، شمارنده‌ها و ابطال‌ها با restart از بین نمی‌روند.

- ارسال مجدد برای challenge فعال: حداقل ۶۰ ثانیه.
- هر موبایل: حداکثر ۵ درخواست در ۱۵ دقیقه (درخواست‌های تکراری هم محاسبه می‌شوند).
- هر IP: حداکثر ۳۰ درخواست OTP و ۶۰ درخواست verify در ۱۵ دقیقه.
- پاسخ 429 شامل Retry-After است.

به X-Forwarded-For خام اعتماد نمی‌شود. پشت Next/Nginx، بدون تنظیم trust proxy،
IP می‌تواند برای همهٔ کاربران IP پراکسی باشد و محدودیت مشترک ایجاد کند. در استقرار
واقعی، فقط IP/CIDR پراکسی کنترل‌شده را با TRUST_PROXY مشخص و هدرهای ورودی را در
لبه بازنویسی کنید؛ API را مستقیماً به اینترنت عرضه نکنید.

## تنظیمات production

`NODE_ENV=production` باید برای **سرویس API جداگانه** تنظیم شود؛ production بودن
Next.js به‌تنهایی API را به این حالت نمی‌برد. `NIMKAT_SECRET` تصادفی حداقل ۳۲کاراکتری
الزامی است. تنظیم COOKIE_SECURE=false در production مانع startup می‌شود.
APP_ORIGINS فهرست exact originهای مجاز است؛ wildcard مجاز نیست.
.env.example الگو است؛ API آن فایل را خودکار بارگذاری نمی‌کند.

قرارداد adapter پیامک: `sendOtp(mobile, code): Promise<void>` به ماژول auth تزریق
می‌شود. آن را در composition root متصل کنید؛ API key و URL سرویس باید در سمت سرور
بمانند و خطای provider نباید credential یا کد را به پاسخ خطا/لاگ بریزد.

## مهاجرت و تست

migration افزایشی جدول‌های auth_sessions/auth_refresh_used/auth_limits را ایجاد
و OTPهای plaintext قدیمی را باطل می‌کند؛ اطلاعات کاربران و رزروها حذف نمی‌شوند.
NIMKAT_DATA_DIR برای تست روی دیتابیس جدا پشتیبانی می‌شود.

`npm test` در backend از SQLite حافظه‌ای و ساعت قابل‌کنترل برای آزمون expiry،
rotation، replay، logout، CSRF، rate limit، حالت production و migration استفاده می‌کند.
Playwright جریان واقعی فرم OTP فارسی، reload، HttpOnly و logout/replay را بررسی می‌کند.
تست مرورگر را فقط روی DB آزمایشی اجرا کنید؛ اجرای مکرر در یک بازه ممکن است به‌درستی
با rate limit مواجه شود، بنابراین از دیتابیس تازهٔ آزمایشی استفاده کنید.

## باقی‌مانده

SMS adapter واقعی، انتقال session/limiter به Redis و دادهٔ اصلی به PostgreSQL،
audit امنیتی کامل، فهرست دستگاه‌ها و ابطال انتخابی در UI (دکمهٔ خروج از همه دستگاه‌ها اضافه شده است)، کنترل teacher approval و آزمون بار/نفوذ.
این مرحله جایگزین ممیزی امنیتی مستقل نیست.

## اصلاح بازگشت به لاگین و پیش‌نمایش تعبیه‌شده
پاسخ دیرهنگام bootstrap ناشناس نمی‌تواند ورود OTP جدید را بازنویسی کند؛
نسخهٔ نشست در AuthProvider و API client بررسی می‌شود. هدایت پس از commit شدن
کاربر انجام می‌شود و next=/login پذیرفته نمی‌شود.
برای iframe میان‌سایتی در پیش‌نمایش HTTPS، سرور جاری با COOKIE_SECURE=true،
COOKIE_SAME_SITE=none و COOKIE_PARTITIONED=true اجرا شده است. پیش‌فرض پروژه
همچنان Lax است؛ بدون Secure، سیاست None/Partitioned در راه‌اندازی رد می‌شود.
CSRF و کنترل Origin حذف نشده‌اند. مرورگرهای فاقد پشتیبانی از کوکی پارتیشن‌شده
یا با مسدودسازی کامل کوکی ممکن است نیاز به بازکردن پیش‌نمایش در زبانهٔ مستقل داشته باشند.
آزمون Chromium ورود و reload داخل iframe میان‌سایتی را پوشش می‌دهد؛ در مرورگر
آزمون فقط محدودیت شبکهٔ محلی برای اتصال دو آدرس loopback غیرفعال است، نه سیاست کوکی.

### تأیید نشست پس از OTP (۲۰ اکتبر ۲۰۲۶)
موفقیت پاسخ OTP به‌تنهایی ورود محسوب نمی‌شود: کلاینت ابتدا `/auth/me` را
با کوکی بررسی می‌کند. اگر مرورگر کوکی را ذخیره نکرده باشد، در همان فرم خطای
قابل‌فهم و امکان بازکردن زبانهٔ مستقل نشان داده می‌شود، نه هدایت رفت‌وبرگشتی.
خطای موقت 5xx در refresh کاربر را خارج نمی‌کند؛ خطای 401 گفتگوی مهمان نیز نشست
حساب را پاک نمی‌کند. آخرین کوکی CSRF هم‌نام انتخاب می‌شود و هنگام تغییر سیاست
Partitioned، کوکی سیاست مقابل منقضی می‌شود.
آزمون مرورگر مسدودبودن کوکی، bootstrap دیرهنگام، reload در iframe و خروج واقعی
را پوشش می‌دهد. این پوشش Chromium است؛ ادعای سازگاری همهٔ مرورگرها نیست.
