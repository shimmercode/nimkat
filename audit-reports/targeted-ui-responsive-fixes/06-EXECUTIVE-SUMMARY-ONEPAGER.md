## ۱) نیمکت چیست؟

> سامانهٔ کامل آموزش آنلاین: کاربر ثبت‌نام می‌کند → کلاس پیدا می‌کند → رزرو می‌گیرد → پرداخت می‌کند → در کلاس آنلاین حاضر می‌شود → گزارش می‌گیرد → امتیاز و کیف پول دارد.

## ۳) معماری — همه‌چیز روی یک سرور

```
مرورگر ──► Nginx (:80/:443) ──┬──/api/──────► BACKEND (Node 22 + Express) ──► SQLite (WAL)
                                └──/──────────► FRONTEND (Next.js 16 SSR)
```
- **۳ جزء**: فرانت‌اند (Next.js 16 + React 19 + Tailwind 4 + Radix) · بک‌اند (Node 22 + Express 5) · پایگاه‌داده (SQLite/WAL) + Nginx
- **یک سرور کافی است** → هزینه نصف، تأخیر صفر بین فرانت و بک‌اند

## ۴) سه نقطهٔ قوت کلیدی

| # | موضوع | چرا مهم است |
|---|---|---|
| **۱** | **دفترداری دوطرفه + Idempotence** | هر تراکنش دو ورودی متوازن دارد. **سرور** مرجع است نه مرورگر. کال‌بک تکراری درگاه ⇒ پول دو بار حساب نمی‌شود. |
| **۲** | **سوابق مالی/امتیازی غیرقابل‌دستکاری** | ۷ جدول باشگاه با Trigger دیتابیس **فقط-افزودنی** شده‌اند؛ حتی کدِ سامانه هم نمی‌تواند حذف یا ویرایش کند. |
| **۳** | **حضور و غیاب ضدّتقلب** | `event_id` یکتا + هش SHA-256. همان شناسه با محتوای متفاوت ⇒ رد می‌شود. ورود/خروج فقط ±۱۵ دقیقه نسبت به جلسه معتبر است. |

## ۶) وضعیت فعلی — «دمو» یعنی چه؟

| کامل و آمادهٔ بهره‌برداری | در حالت آزمایشی (نیازمند دسترسی) |
|---|---|
| ✅ کل طراحی و رابط کاربری (۵۵ صفحه) | 🟡 **درگاه پرداخت** — نیاز: Merchant ID + کلید API |
| ✅ تمام پنل‌ها و منطق کسب‌وکار | 🟡 **OTP / پیامک** — نیاز: API Key + الگوی Verify |
| ✅ پایگاه‌داده (۱۰۱ جدول) + مجوز نقش + Audit | 🟡 **اسکای‌روم** — نیاز: API Key حساب سازمانی |
| ✅ ویرایشگر بصری با نسخه‌بندی و بازگردانی | 🟡 **تست بار و فشار** — نیاز: سرور نهایی با منابع کافی |
| ✅ تست کامل (۸۷ + ۱۲۱ + ۱۱۵) | 🟡 **دامنهٔ اختصاصی** — نیاز: DNS |

> **اصل ما:** هیچ موفقیتی برای پرداخت، رزرو، ورود به کلاس یا دریافت پاداش **شبیه‌سازی و به‌عنوان واقعیت اعلام نشده**. هرجا محدودیت بوده، صریح گفته شده.

## ۱۰) تست‌های بار — چرا در مرحلهٔ آخر؟

> «اگر روی زیرساخت موقت دمو تست کنیم، نتیجه **ملاک معتبری** برای پایداری محصول در مقیاس واقعی نیست.»

| حوزه | شاخص کلیدی |
|---|---|
| بار هم‌زمان سرور | TTFB، نرخ خطا، CPU/RAM |
| بار رزرو روی ظرفیت محدود | **عدم بیش‌رزرو**، صحت قفل صندلی |
| بار تأیید و **کال‌بک** | **Idempotence**، یکپارچگی تراکنش |
| بار **کیف پول** و تسویه | **عدم Race Condition**، تراز موجودی |
| بار چت‌روم | تأخیر پیام، پایداری اتصال |
| بار کلاس آنلاین | صحت ثبت حضور، عدم اشغال ظرفیت |
| پایداری (Soak) | نشت حافظه، رشد دیتابیس |
| بازیابی پس از قطعی | بازیابی، حفظ داده، عدم از دست رفتن تراکنش |

## ۱۱) پرسش‌های پرتکرار + پاسخ آماده

| پرسش | پاسخ یک‌خطی |
|---|---|
| **زمان تا بهره‌برداری کامل؟** | با دریافت دسترسی‌ها: ۱–۲ روز کاری |
| **هزینهٔ ماهانه؟** | ~۳٫۴–۳٫۵ میلیون تومان |
| **تغییر محتوا با چه سرعتی؟** | از ویرایشگر بصری، چند دقیقه — توسط خود کارفرما |
| **داده‌ها کجا ذخیره می‌شوند؟** | روی سروری که کارفرما تهیه می‌کند، **داخل ایران**، با بکاپ روزانه |
| **امکان توسعهٔ بیشتر؟** | بله — ماژولار و دیتابیس رابطه‌ای. در مقیاس خیلی بزرگ، مهاجرت به PostgreSQL |
| **مالکیت کد؟** | کد در مخزن گیت شما با تاریخچهٔ کامل |
| **چطور از خرابی جلوگیری می‌شود؟** | ۳ لایه: health check با rollback خودکار + بکاپ روزانه + تست خودکار قبل از انتشار |
| **چه چیزی را نمی‌توانید انجام دهید؟** | تا دریافت کلید سرویس‌ها و سرور نهایی: پرداخت واقعی، پیامک واقعی، اسکای‌روم، تست بار — و **این را به‌عنوان انجام‌شده اعلام نمی‌کنیم** |
| **محدودیت ظرفیت فعلی؟** | دمو روی زیرساخت اشتراکی است. با پلن ۴/۸/۱۰۰ تا ~۲۰۰ کاربر فعال هم‌زمان با آسودگی پاسخگویی می‌شود |
