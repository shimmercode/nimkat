# بخش ۱ — بک‌اند (API و منطق کسب‌وکار)

## ۱-۱) اجرای سامانه

```
                    ┌─────────────────────────────┐
   مرورگر کاربر ──► │   Nginx  (Reverse Proxy)     │
                    │   :80  /  :443               │
                    └──────┬───────────────┬───────┘
                           │               │  بقیهٔ مسیرها
              مسیر /api     │               ▼
                           ▼        ┌────────────────────┐
              ┌──────────────────┐  │      FRONTEND      │
              │   BACKEND / API  │  │   Next.js 16 SSR   │
              │  Node.js 22      │  │   React 19         │
              │  Express 5       │  │   Tailwind 4       │
              │  :8000 (داخلی)   │  │   :5173 (داخلی)    │
              │  ۱۴ ماژول        │  └────────────────────┘
              │  ۲۰۹ endpoint    │            │
              └────────┬─────────┘            │  proxy /api/*
                       ▼                      │
              ┌──────────────────┐            │
              │    SQLite (WAL)  │◄───────────┘
              │   /data (Volume) │
              └──────────────────┘
```

**چرا یک سرور کافی است:** فرانت‌اند و بک‌اند دو سرویس جدا روی دو ماشین نیستند؛ داخل شبکهٔ خصوصی Docker به هم وصل‌اند و فقط از طریق Nginx در دسترس کاربر هستند. نتیجه: هزینهٔ سرور نصف، تأخیر بین فرانت و بک‌اند روی لوکال‌هاست صفر، و پیچیدگی اپراتور کمتر.

## ۱-۳) احراز هویت و امنیت

| موضوع | پیاده‌سازی |
|---|---|
| ورود | **OTP پیامکی** روی `09xxxxxxxxx` — بدون رمز عبور |
| انقضای OTP | محدود و منقضی‌شونده |
| حداکثر تلاش | **۵ تلاش** |
| محدودیت نرخ | بر پایهٔ **IP** و **شمارهٔ موبایل** — پنجرهٔ ۱۵ دقیقه |
| کوکی نشست | `httpOnly` + `Secure` + `SameSite` — غیرقابل دسترسی از جاوااسکریپت |
| دامنهٔ توکن | فقط `/api` (نه کل سایت) |
| تازه‌سازی توکن | فقط `/api/auth` |
| CSRF | توکن اختصاصی + بررسی هم‌مبدأ |
| هش OTP | **HMAC + pepper** — کد خام ذخیره نمی‌شود |
| گارد محیط تولید | `COOKIE_SECURE=false` در production ⇒ برنامه **خطا می‌دهد و بالا نمی‌آید** |

## ۲-۲) لایهٔ پروکسی API

فرانت‌اند **مستقیماً** به بک‌اند وصل نمی‌شود. یک Route Handler در `frontend/src/app/api/[...path]/route.ts` نقش reverse proxy را دارد:

- **فقط headerهای allowlist‌شده** عبور می‌کنند (cookie, content-type, authorization, `idempotency-key`, `x-csrf-token`, `x-support-token` …) — بقیه حذف می‌شوند
- **پاسخ‌ها** هم allowlist دارند (cache-control, content-disposition, retry-after, `x-ratelimit-*` …)
- **ترتیب مقصد:** ابتدا بک‌اند داخلی (`127.0.0.1:8000`)، سپس در صورت نیاز مبدأ پیکربندی‌شده
- **بدون retry روی متدهای نوشتنی** — تا idempotence نشکند

# بخش ۳ — یکپارچگی فرانت ↔ بک

## ۳-۱) جریان یک درخواست

```
مرورگر
  │  fetch('/api/classes?subject=math')
  ▼
Next.js Route Handler  (frontend/src/app/api/[...path]/route.ts)
  │  · اجازهٔ فقط headerهای allowlist‌شده
  │  · حذف headerهای hop-by-hop
  ▼
127.0.0.1:8000  (بک‌اند داخلی)  ←  fallback: مبدأ پیکربندی‌شده
  │
  ▼
Express 5  →  ماژول مربوطه  →  SQLite (WAL)
```

**نقاط کنترلی امنیت:**
1. بک‌اند هرگز به‌تنهایی در معرض اینترنت نیست — فقط Nginx
2. پروکسی فرانت headerهای ناشناس را دور می‌ریزد
3. نقش‌ها در بک‌اند بررسی می‌شوند (`requireRole`) — فرانت فقط لایهٔ نمایش است
4. SSE با `proxy_buffering off` تا رویدادها بلادرنگ برسند

| **تست بار و فشار** | اجرا نشده | نیازمند سرور واقعی با منابع کافی |
| **دامنهٔ اختصاصی** | روی زیرساخت Render | نیازمند DNS |

## ۶-۳) دسترسی‌های لازم از کارفرما

| # | دسترسی | برای چه |
|---|---|---|
| ۱ | **درگاه پرداخت:** Merchant ID، کلید API، اطلاعات تسویه | اتصال Live + تست Callback |
| ۲ | **سرویс پیامک:** کلید API، شمارهٔ فرستنده، الگوی Verify | ارسال OTP واقعی |
| ۳ | **SkyRoom:** API Key و حساب سازمانی | لینک جلسه + حضور و غیاب |
| ۴ | **دامنه + DNS** | اتصال به سرور ایران |
| ۵ | **سرور تولیدی با SSH** | استقرار + تست بار |
| ۶ | **سرویس ایمیل (SMTP)** | اعلان رزرو، لغو، یادآوری |
| ۷ | **سرویس مانیتورینگ** (اختیاری) | هشدار خطا |
| ۸ | **اطلاعات هویتی/حقوقی برند** | نهایی‌سازی متن‌های رسمی |
| ۹ | **اطلاعات مالی استادان (شبا)** | فعال‌سازی برداشت و گزارش درآمد |

## ۶-۴) چرا تست بار حتماً باید روی سرور واقعی باشد

> «اگر روی زیرساخت موقت دمو تست کنیم، نتیجه **ملاک معتبری** برای پایداری محصول در مقیاس واقعی نیست. به همین دلیل تست بار، استرس، پایداری طولانی و بازیابی پس از قطعی، همگی در **مرحلهٔ آخر** روی سرور نهایی با پیکربندی تولیدی اجرا می‌شوند.»

| حوزه | سناریو | شاخص |
|---|---|---|
| بار سرور | اوج ترافیک هم‌زمان | TTFB، نرخ خطا، CPU/RAM |
| بار ورود | انبوه درخواست OTP هم‌زمان | زمان پاسخ، ۴۲۹، Rate Limit |
| بار رزرو | تقابل روی ظرفیت محدود | **عدم بیش‌رزرو**، صحت قفل صندلی |
| بار تأیید | Callback تکراری | **Idempotence**، یکپارچگی تراکنش |
| بار کال‌بک | کال‌بک هم‌زمان و تکراری | تحمل تکرار، صحت دفتر مالی |
| بار کیف پول | برداشت/شارژ/تسویه هم‌زمان | **عدم Race Condition**، تراز موجودی |
| بار چت‌روم | کاربران هم‌زمان در یک اتاق | تأخیر پیام، پایداری |
| بار کلاس آنلاین | ورود هم‌زمان به اسکای‌روم | کیفیت لینک، صحت حضور |
| پایداری (Soak) | اجرای طولانی زیر بار | نشت حافظه، رشد دیتابیس |
| بازیابی | قطع و بازگشت سرویس | بازیابی، حفظ داده |

# بخش ۷ — جمع‌بندی

> «وضعیت ما: **طراحی کامل، پیاده‌سازی کامل، تست کامل.** سامانه الان روی سرور قابل مشاهده است و همهٔ بخش‌های اصلی کار می‌کنند.
>
> کاری که **باقی مانده** دو چیز است: **اتصال به سرویس‌های بیرونی** (درگاه، پیامک، اسکای‌روم) که نیازمند دسترسی فنی و مالی شماست، و **اعتبارسنجی عملیاتی** (تست بار و فشار) که ذاتاً نیازمند سرور نهایی است.
>
> به‌محض دریافت این دسترسی‌ها وارد **مرحلهٔ نهایی** می‌شویم: پیکربندی امن سرویس‌ها، اجرای چرخهٔ کامل کاربر، تست بار روی سرور واقعی، اتصال دامنه و تحویل نهایی.»
