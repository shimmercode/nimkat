### سه نقطهٔ قوت اصلی

**۱) مالی — دفترداری دوطرفه**
هر تراکنش دو ورودی متوازن دارد؛ پول از هیچ‌جا وارد/خارج نمی‌شود. **سرور** مبلغ و وضعیت پرداخت را تعیین می‌کند، نه مرورگر. هر تراکنش کلید یکتا دارد ⇒ کال‌بک تکراری پول را دوباره حساب نمی‌کند. رزرو صندلی هنگام انتخاب قفل می‌شود و در صورت پرداخت‌نشدن آزاد می‌شود ⇒ **عدم بیش‌رزرو**. شبا با استاندارد **mod-97** اعتبارسنجی می‌شود.

**۲) باشگاه — سوابق غیرقابل دستکاری**
جدول‌های `loyalty_ledger`, `loyalty_events`, `loyalty_awards`, `loyalty_medals`, `loyalty_session_checks`, `loyalty_surveys`, `loyalty_academic` همگی با **Trigger** در سطح دیتابیس **فقط-افزودنی** شده‌اند:
```sql
CREATE TRIGGER loyalty_ledger_no_update BEFORE UPDATE ON loyalty_ledger
BEGIN SELECT RAISE(ABORT,'append-only loyalty record'); END;
```
حتی کدِ خودِ سامانه هم نمی‌تواند رکورد امتیازی را حذف یا ویرایش کند.

**۳) حضور و غیاب — ضدّتقلب**
رویداد حضور با `event_id` یکتا + **هش SHA-256** محتوا ثبت می‌شود. همان `event_id` با محتوای متفاوت ⇒ رد با خطای ۴۰۹. لینک اسکای‌روم فقط `https:` و دامنهٔ `skyroom.online` را می‌پذیرد (جلوگیری از SSRF) و دسترسی **بعد** از فراخوانی شبکه دوباره بررسی می‌شود.

### امنیت
ورود با **OTP پیامکی** · حداکثر ۵ تلاش · محدودیت نرخ بر پایهٔ IP و موبایل · کوکی `httpOnly + Secure + SameSite` · توکن فقط روی `/api` · **CSRF + بررسی هم‌مبدأ** · کد OTP با **HMAC + pepper** هش می‌شود (کد خام ذخیره نمی‌شود).

### نکتهٔ معماری — پروکسی API
فرانت‌اند مستقیم به بک‌اند وصل نمی‌شود. یک Route Handler فقط headerهای allowlist‌شده را عبور می‌دهد و headerهای hop-by-hop را حذف می‌کند. **نقش‌ها در بک‌اند بررسی می‌شوند** — فرانت فقط لایهٔ نمایش است.

## استقرار

```
مرورگر → Nginx (:80/:443)
           ├─ /api/* → BACKEND  Node 22 · Express 5 · :8000 (داخلی)
           └─ /*     → FRONTEND Next.js 16 SSR · :5173 (داخلی)
                          ↓
                    SQLite (WAL) → Volume: nimkat_data:/data
```

**یک سرور کافی است** — فرانت و بک‌اند داخل شبکهٔ خصوصی Docker به هم وصل‌اند. هزینهٔ سرور نصف، تأخیر صفر، پیچیدگی کمتر.

- **منابع پیشنهادی:** ۴ vCPU · ۸ گیگ RAM · ۸۰–۱۰۰ گیگ NVMe · Ubuntu 22.04/24.04 یا Debian 12 · **سرور ایران**
- **بکاپ:** روزانه با `sqlite3 .backup` (به‌دلیل WAL، کپی ساده ناقص می‌شود)
- **استقرار:** `deploy.sh` با health check و rollback خودکار
- **چرا ایران؟** پینگ پایین · IP ایران برای دامنهٔ `.ir` · **نگهداری دادهٔ کاربران داخل کشور** (الزام قانونی) · Callback درگاه و پیامک بدون محدودیت

## وضعیت فعلی — دمو چیست و چه چیزی در مرحلهٔ نهایی است

**کامل و آمادهٔ بهره‌برداری:** ✅ کل رابط و طراحی (۵۵ صفحه) · ✅ همهٔ پنل‌ها · ✅ **منطق کامل کسب‌وکار** · ✅ دیتابیس ۱۰۱ جدول با مجوزدهی نقش‌محور · ✅ ویرایشگر بصری با نسخه‌بندی · ✅ سیستم تست کامل · ✅ Docker Compose آمادهٔ استقرار

**در دمو آزمایشی است:**

| قابلیت | وضعیت | دلیل |
|---|---|---|
| درگاه پرداخت | Sandbox | نیازمند Merchant ID و کلید API |
| OTP / پیامک | بازگردانی کد | نیازمند API Key پیامک + الگوی Verify |
| اسکای‌روم | بدون کلید API | نیازمند حساب سازمانی |
| چت بلادرنگ روی سرور تولیدی | پیاده‌سازی‌شده | نیازمند سرور نهایی |

| دامنهٔ اختصاصی | روی Render | نیازمند DNS |

**۹ دسترسی لازم از کارفرما:** درگاه پرداخت · سرویس پیامک · SkyRoom · دامنه + DNS · سرور تولیدی با SSH · SMTP · مانیتورینگ (اختیاری) · اطلاعات هویتی/حقوقی برند · اطلاعات مالی استادان (شبا)

> **چرا تست بار باید روی سرور واقعی باشد:** «اگر روی زیرساخت موقت دمو تست کنیم، نتیجه ملاک معتبری برای پایداری محصول در مقیاس واقعی نیست.»
>
> پوشش تست بار: بار سرور · بار ورود (OTP انبوه) · بار رزرو (**عدم بیش‌رزرو**) · بار تأیید (**Idempotence**) · بار کال‌بک تکراری · بار کیف پول (**عدم Race Condition**) · بار چت‌روم · بار کلاس آنلاین · پایداری (Soak) · بازیابی پس از قطعی
