# بخش ۱ — معماری کلی و سیستم مهندسی

## ۱-۱) اجزای سامانه

سامانه از **سه جزء اصلی** تشکیل شده که با Docker Compose روی یک سرور اجرا می‌شوند:

```
                    ┌─────────────────────────────┐
   مرورگر کاربر ──► │   Nginx  (Reverse Proxy)     │
                    │   :80  /  :443               │
                    └──────┬───────────────┬───────┘
                           │               │
              مسیر /api     │               │  بقیهٔ مسیرها
                           ▼               ▼
              ┌──────────────────┐  ┌────────────────────┐
              │   BACKEND / API  │  │      FRONTEND      │
              │  Node.js 22      │  │   Next.js 16 SSR   │
              │  Express 5       │  │   React 19         │
              │  :8000 (داخلی)   │  │   Tailwind 4       │
              │  ۱۴ ماژول       │  │   :5173 (داخلی)    │
              └────────┬─────────┘  └────────────────────┘
                       ▼
              ┌──────────────────┐
              │    SQLite (WAL)  │
              │   /data (Volume) │
              └──────────────────┘
```

## ۱-۲) چرا یک سرور کافی است

فرانت‌اند و بک‌اند **دو سرویس جدا نیستند** که روی دو ماشین باشند. هر دو داخل یک شبکهٔ خصوصی Docker به هم وصل‌اند و فقط از طریق Nginx در دسترس کاربر هستند. این یعنی:
- **هزینهٔ سرور نصف** می‌شود
- تأخیر بین فرانت و بک‌اند **صفر** است (روی لوکال‌هاست)
- پیچیدگی اپراتور کمتر

## ۱-۳) کیفیت کد و تست

| لایه | ابزار | وضعیت |
|---|---|---|
| تست واحد فرانت‌اند | Vitest | ۱۰ فایل / ۸۷ تست ✅ |
| تست واحد بک‌اند | `node --test` | ۱۲۱ تست ✅ |
| تست پذیرش مرورگری | Playwright + Chromium | ۱۱۵ بررسی روی ۱۲ سایز نمایشگر ✅ |
| بررسی نوع‌ها | TypeScript (`tsc --noEmit`) | بدون خطا ✅ |
| بیلد تولید | Next.js webpack | ۴۸/۴۸ مسیر ✅ |

**سیستم مهندسی که رعایت شده:**
- **Commit‌های کوچک و معنادار** با پیام کامل — تاریخچهٔ کامل تغییرات قابل بازبینی
- **Restore کارهای ناتمام** (restore) با `git reset --soft` به‌جای حذف فایل
- **هیچ فایل یا داده‌ای بدون بررسی حذف نشده** — همه‌چیز قابل بازگشت
- **بدون force push** و **بدون حذف شاخه** — تاریخچه هرگز بازنویسی نمی‌شود

## ۱-۴) اگر پرسید «چقدر این کد قابل نگهداری است؟»

> «پروژه **ماژولار** است: ۱۴ ماژول مستقل بک‌اند، هرکدام با مسئولیت مشخص. هیچ فایل بک‌اند بزرگ‌تر از چند صد خط نیست. فرانت‌اند هم بلوک‌بندی شده: هر بخش صفحه یک بلوک مستقل است که در ویرایشگر بصری هم قابل استفاده است. تغییر یک بلوک، بقیهٔ صفحه را نمی‌شکند.»

## ۲-۲) احراز هویت و امنیت

**پاسخ به «چطور ورود کاربران کنترل می‌شود؟»**

| موضوع | پیاده‌سازی |
|---|---|
| ورود | **OTP پیامکی** روی شمارهٔ موبایل (`09xxxxxxxxx`) — بدون رمز عبور |
| مدت اعتبار OTP | محدود و منقضی‌شونده |
| حداکثر تلاش | **۵ تلاش** برای ورود |
| محدودیت نرخ | بر اساس **IP** و **شمارهٔ موبایل** — پنجرهٔ ۱۵ دقیقه‌ای |
| کوکی نشست | `httpOnly` + `Secure` + `SameSite` — **غیرقابل دسترسی از جاوااسکریپت** |
| توکن دسترسی | فقط روی مسیر `/api` (نه کل سایت) |
| توکن تازه‌سازی | فقط روی `/api/auth` |
| CSRF | توکن اختصاصی + بررسی هم‌مبدأ |
| هش کد OTP | با **HMAC** و pepper — کد خام ذخیره نمی‌شود |
| کوکی در production | `COOKIE_SECURE=false` در محیط تولید ⇒ **برنامه خطا می‌دهد و بالا نمی‌آید** |

> 💡 **نکتهٔ قوت برای ارائه:** «کد تأیید به‌صورت خام در پایگاه‌داده ذخیره نمی‌شود؛ با کلید مخفی هش می‌شود. یعنی حتی کسی که به دیتابیس دسترسی داشته باشد، نمی‌تواند کدهای ورود را بخواند.»

## ۲-۳) منطق مالی — مهم‌ترین بخش از نظر کارفرما

**پاسخ به «پول و تراکنش‌ها چطور مدیریت می‌شود؟»**

| اصل | پیاده‌سازی |
|---|---|
| **دفترداری دوطرفه** | هر تراکنش دو ورودی متوازن دارد (بدهکار/بستانکار). هیچ پولی «از ناکجاآباد» وارد یا خارج نمی‌شود |
| **پایگاه‌داده به‌عنوان مرجع** | **سرور** تصمیم می‌گیرد، نه مرورگر. مبلغ و وضعیت پرداخت هرگز از سمت کاربر خوانده نمی‌شود |
| **Idempotence** | هر تراکنش با کلید یکتا ثبت می‌شود. اگر درگاه پرداخت کال‌بک را **دو بار** بفرستد، پول **دو بار** حساب نمی‌شود |
| **رزرو موقت (Hold)** | هنگام انتخاب کلاس، صندلی موقت رزرو و پرداخت قفل می‌شود. اگر پرداخت انجام نشود، خودکار آزاد می‌شود |
| **حذف بیش‌رزرو** | ظرفیت با شمارش رزروهای تأییدشده کنترل می‌شود؛ رزرو هم‌زمان روی صندلی‌های محدود امن است |
| **حساب شبا** | اعتبارسنجی استاندارد **mod-97** برای شبا (`IR` + ۲۴ رقم) — شمارهٔ نادرست رد می‌شود |
| **سهم استاد** | ۸۵٪ سهم استاد، طبق قرارداد و تنظیمات مالی |
| **تسویه** | دوره‌ای (هر دو هفته)، با ثبت درآمد جلسات و snapshot |

> ⚠️ **نکتهٔ مهم برای پاسخ:** «هیچ‌وقت در این پروژه، موفقیت پرداخت/رزرو/ورود به کلاس/دریافت پاداش به‌صورت شبیه‌سازی‌شده به‌عنوان واقعیت گزارش نشده. هرجا محدودیت بوده، صریح اعلام شده.»

## ۲-۴) باشگاه مشتریان (Club) — سیستم وفاداری

**پاسخ به «باشگاه چطور کار می‌کند؟»**

```
۵ سطح با آستانهٔ صعودی از صفر:
  برنزی (۰) → نقره‌ای (۱۰۰۰) → طلایی (۲۵۰۰) → پلاتینیوم (۵۰۰۰) → سفیر (۱۰۰۰۰+)
  ↑ امتیاز (نه موجودی سکه) — دریافت جایزه امتیاز را کم نمی‌کند
```

| قابلیت | جزئیات |
|---|---|
| **مأموریت‌ها** | روزانه / هفتگی / مناسبتی، هرکدام با شرط مشخص (کلاس موفق، دعوت دوست، تکمیل پروفایل…) |
| **جایزه‌ها (۶ نوع)** | `wallet` (کیف پول) · `manual` (دستی) · `discount` (تخفیف) · `commission` (معافیت کمیسیون) · `customization` (شخصی‌سازی ظاهر) · `coming` (به‌زودی) |
| **گردونه شانس** | هفتگی برای دانش‌آموز، بر اساس تعداد کلاس برای استاد — با وزن‌دهی قابل تنظیم |
| **نشان‌ها** | بر اساس رویداد و میانگین امتیاز با حداقل تعداد ارزیابی |
| **زنجیرهٔ فعالیت** | کلاس موفق + نظرسنجی + نیم‌چت، زنجیره می‌سازد؛ **ورود خالی پاداش ندارد** |
| **تقویم شمسی** | هفته از شنبه و دورهٔ ماهانه بر مبنای تقویم شمسی و **ساعت تهران** |
| **کد معرفی** | کد یکتای ۸ بایتی hex برای هر کاربر |
| **بودجهٔ جایزه** | سقف بودجهٔ کل (Toman) در تنظیمات — کنترل مالی |

**محافظت داده (نکتهٔ بسیار قوی برای ارائه):**
> «جدول‌های سوابق باشگاه — یعنی `loyalty_ledger`، `loyalty_events`، `loyalty_awards`، `loyalty_medals`، `loyalty_session_checks`، `loyalty_surveys`، `loyalty_academic` — همگی با **Trigger** در سطح پایگاه‌داده **فقط-افزودنی** شده‌اند. یعنی حتی کدِ خودِ سامانه هم نمی‌تواند رکورد امتیازی را حذف یا ویرایش کند. سوابق مالی و امتیازی **غیرقابل دستکاری** هستند.»
